# Dev Control Room 사용 가이드

Dev Control Room은 로컬 저장소의 코드 품질을 점검하고 결과를 다시 확인하는
Windows용 도구입니다. Git 관리와 외부 작업은 보조 기능입니다.

이 문서는 v0.17.0의 사용법입니다. Python/FastAPI와 Vue는 구성 확인과 준비
안내까지 지원합니다. 저장소 최상위 폴더의 Go 모듈은 실제 검사를 실행할 수 있습니다.

## 처음 시작하기

이 절은 v0.17.0의 프로젝트 구성 확인 화면을 설명합니다. 선택한 checkout의
구성과 근거를 먼저 읽고, 필요한 준비 안내를 확인하는 흐름입니다.

먼저 저장소 하나를 등록하고, 어떤 언어와 검사 설정이 있는지 확인하세요.
프로그램이 Go로 만들어졌다고 검사 대상도 Go여야 하는 것은 아닙니다.

1. `serve`로 로컬 서버를 시작합니다.
2. `프로젝트`에서 `프로젝트 등록 → 폴더 선택 → 저장소 찾기`를 누릅니다.
   찾은 저장소 중 확인할 대상을 고른 뒤 `선택한 저장소 등록`을 누릅니다.
3. `작업`에서 검사할 저장소와 브랜치를 확인합니다. 대상이 아직 보이지 않으면
   저장소 상태를 새로 고칩니다. 이 작업은 테스트 실행이 아닙니다.
4. 자동 감지 결과에서 백엔드·프런트엔드 등의 구성과 근거 파일을 확인합니다.
   Python/FastAPI, JavaScript·TypeScript/Vue, Go 설정이 함께 있을 수 있습니다.
   `직접 선택`은 표시할 언어별 검사 안내를 좁히는 UI 필터입니다. 혼합 저장소의
   다른 구성과 근거를 숨기지 않으며, 선택만으로 설정이 생성되거나 설치되지는
   않습니다.
5. 필요한 검사의 `준비와 근거 보기`를 엽니다. 기존 설정과 준비가 필요한 항목을
   구분해 읽습니다. M1은 선택한 checkout 아래를 깊이 3, 디렉터리 항목 2,000개,
   인식 가능한 파일 64개, 파일당 128 KiB 범위로 읽습니다. 명령은 미리보기이며 자동
   실행하지 않습니다. Python/FastAPI와 Vue의 M1 지원은 구성 근거와 준비 안내까지입니다.
6. 저장소 루트에 Go 설정이 있는 경우 기존 루트 대상 정적 검사·테스트/커버리지
   실행을 사용할 수 있습니다. 실제 결과는 같은 화면에서 확인하고
   `검증 결과에서 보기`로 상세 근거를 엽니다. M1이 Python/Vue 분석을 실행하는
   것은 아니며, 도구나 대상이 없으면 통과가 아니라 사용할 수 없는 상태입니다.

언어 선택은 같은 대상과 구성 근거에 한해 기억하는 표시 설정입니다. HEAD나 구성
근거가 바뀌면 자동 감지로 되돌아갑니다. 아직 실행하지 않은 도구의 설치 여부나
테스트 성공을 설정 파일만으로 판단하지 않습니다. 모든 선택 도구를 설치할 필요는
없고, AI 제안이나 자동 설치도 M1에 포함되지 않습니다.

`저장소 상태 새로 고침` 같은 전역 Git 새로 고침은 Git·Worktree 관찰값을
갱신할 뿐 품질 검사를 실행하지 않으며, `검증` 결과를 만들지 않습니다.

저장소 등록과 읽기 전용 점검은 원본 파일을 바꾸지 않습니다. 결과가 없을 때
`검증`의 `예시 화면 보기`를 열면 실제 기록에 포함되지 않는 샘플 흐름을 볼 수
있습니다.

## 화면별 역할

| 화면 | 하는 일 |
| --- | --- |
| 개선 | 검사할 저장소를 선택하고 최근 검사와 저장소 확인 항목을 봅니다. |
| 프로젝트 | 등록한 프로젝트·저장소·Worktree를 확인하고 범위를 관리합니다. |
| 작업 | 저장소의 언어·검사 설정과 준비 방법을 확인합니다. 지원되는 검사만 실행합니다. |
| 검증 | 반복 실행 가능한 점검, 효과, 사용량, artifact 근거를 확인합니다. |
| 진단 | 필수 도구와 연결한 Provider, Agent Profile, Jenkins 설정을 확인합니다. |
| 활동 | 등록·점검·계획·실행 기록을 시간순으로 봅니다. |
| 사용법 | 실제 버튼 순서, 완료 기준, 화면 간 이동을 다시 확인합니다. |

## v0.17.0 M1에서 확인할 범위

- Python/FastAPI, Vue, JavaScript·TypeScript, Go의 인식된 manifest/configuration
  근거를 프로젝트·구성 단위로 보여주고, 기존 설정·준비 필요·지원 불가·판단
  보류를 구분합니다.
- Python/FastAPI와 Vue는 M1에서 실제 analyzer·test runner를 실행하지 않습니다.
  준비 명령과 변경 파일은 미리보기이며, 설치·lockfile 변경·설정 쓰기는 별도
  검토와 승인이 필요합니다.
- 기존 Go 정적 검사(`go vet`)와 테스트·커버리지는 저장소 루트의 기존 실행
  경로만 유지합니다. 설정 파일 존재만으로 도구 설치, 테스트 성공, coverage를
  추정하지 않습니다.
- Go 모듈 또는 필요한 도구를 확인할 수 없는 상태는 성공·통과가 아닙니다.
  도구 상태를 해결한 뒤 다시 실행해야 합니다.

후보 확인에서 프로젝트 등록, 자동 감지, 직접 선택, 새로 고침, 사용법 슬라이드
재진입, Work·Guide·검증 결과 화면의 데스크톱·좁은 화면 흐름을 확인했습니다.
세부 fixture·브라우저 수치와 전체 gate 결과는
[`docs/VERIFICATION_v0.17.0.md`](VERIFICATION_v0.17.0.md)에 기록합니다.

## 기존 점검 기준과 저장소 작업 (고급)

새 `코드 검사` 흐름과 기존 점검 기준·Git 작업은 별도 경로입니다.

`기존 점검 찾기`의 발견 기능은 읽기 전용이며, 현재 다음 두 종류만 다룹니다.

- `package.json`의 문자열 패키지 스크립트
- GitHub Actions workflow의 모호하지 않은 한 줄 `run:` 명령

발견은 후보를 기록할 뿐 임의의 명령을 실행하거나 Go 명령을 추정하지 않습니다.
의존성 설치나 다중 줄·모호한 CI 명령도 이 기능의 성공으로 보지 않습니다.

Checkset은 사람이 적용한 제안과 그 제안에 포함된 정확한 typed command에
묶입니다. 현재 자동으로 typed command로 인정되는 기존 CI 명령은 다음 세 가지뿐입니다.

- `git status --porcelain`
- `git diff --check`
- `git diff --exit-code`

따라서 새 `코드 검사`의 `go vet`나 `go test`를 임의의 Checkset 명령으로
등록할 수 있다고 해석하면 안 됩니다. 기존 점검을 이어갈 때만
`기존 점검 찾기 → 제안 적용 → Checkset 만들기 → 적용 → 실행` 순서로 진행하고,
실행 전에는 명령·제한 시간·HEAD·원본 digest를 확인합니다.

## 무엇을 자동으로 하고, 무엇을 사람이 결정하나요?

- 자동 확인: Git·Worktree 상태, 점검 명령, 종료 코드, HEAD, digest, artifact
  연결을 로컬에서 기록합니다.
- AI Agent: 필요한 경우 제안과 해석을 돕고, 허용된 범위의 Handoff를 준비합니다.
  점검 기준이나 외부 실행을 대신 승인하지 않습니다.
- 사람의 결정: 제안 적용, Worktree 신뢰, Jenkins·릴리스·정리 실행을 승인합니다.

따라서 이 도구의 핵심은 AI에게 바로 맡기는 것이 아니라, 같은 기준으로 다시
확인할 수 있는 품질 기록과 승인 경계를 남기는 데 있습니다.

## 외부 작업과 Jenkins

Jenkins 연동은 `진단 → 실행 설정`에서 등록합니다. 외부 작업을 실행할 때는
다음 순서를 지킵니다.

1. Worktree와 대상 revision을 확인합니다.
2. 외부 작업 계획을 만듭니다.
3. 화면에서 계획과 digest를 검토하고 Worktree를 실행 대상으로 표시합니다.
4. 사람이 승인합니다.
5. 승인된 계획만 실행하고 결과를 `검증`과 `활동`에서 확인합니다.

MCP의 `jenkins.plan`도 2번까지만 수행하며 Jenkins에 접속하지 않습니다.
`jenkins.trigger`는 이미 사람이 승인한 계획만 실행하고, MCP 스스로 승인할
수 없습니다. 비밀 값과 임의 shell/file-read 기능은 MCP에 노출하지 않습니다.

## 문제가 생겼을 때

- 폴더 선택을 취소하면 등록 화면은 그대로 유지됩니다.
- 필수 도구가 없으면 `진단`에서 설치·경로 상태와 다음 조치를 확인합니다.
- 계획이 오래되었거나 Worktree가 바뀌면 실행하지 말고 새 계획을 만듭니다.
- 실패 결과는 지우기보다 `검증`과 `활동`에서 근거를 먼저 확인합니다.

## 작업을 넘기기 전 확인

이 후보의 native Full source gate와 최종 브라우저 확인은 통과했습니다. 다만
Windows OS 폴더 선택 대화상자는 아직 확인하지 않았고, 경로 입력을 통한 등록만
확인했습니다. 패키지·CI·게시 결과와 남은 경계는
[`docs/VERIFICATION_v0.17.0.md`](VERIFICATION_v0.17.0.md)에서 확인합니다.
