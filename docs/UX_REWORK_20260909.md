# Usability-first rework

Status: in progress, not released. Baseline: v0.16.0 / main 5bded0e.

## Product job

Help a developer select a repository, run its existing quality checks, find
actionable problems, and repeat the same checks after a fix. Git inventory,
agent handoff and external operations support this job; they are not the first
thing a new user must understand. Astra is used for development, not added as
an application integration.

## Observed problems

- The live browser retained old project data while the local server was offline.
  Home and diagnostics repeated fetch failures and retries across sections.
- Home repeated queue headings and a second “next action” section instead of
  offering a concrete project/check entry point.
- The global “지금 점검” action invokes repository observation, not the test suite.
- Registration ends in inventory; the next quality-check action is unclear.
- Repository discovery counts filesystem entries, not repositories. Its bounded
  limit can discard partial discoveries. The user's exact original error has
  not been reproduced; this is a source-confirmed failure path.
- Internal terms (QualityHome, Checkset, Finding, manifest, raw identities) leak
  into ordinary tasks. Optional configuration and frequent tasks compete.
- Tall, flat rows and repeated section headers spread related information apart.
- Restoring the release server and clicking existing-check discovery on this
  repository returned zero commands. All current CI commands are multiline,
  deliberately excluded by the narrow discovery parser. More importantly,
  `reviewedTypedCommand` supports only three Git commands. The existing Go
  quality runners have HTTP endpoints but no run form in Work. A visual-only
  checkset redesign would therefore leave the primary use case blocked.

## Visual direction

This is a developer's daily quality workbench, not a promotional dashboard.
Keep locally bundled Pretendard for Korean headings/body and Cascadia/Consolas
for paths and commands. Use the existing white/light-gray surfaces, dark ink,
restrained teal action color, and semantic error/success colors. No cream,
decorative status bars, oversized hero, or empty score cards. Use the existing
4/8/12/16/24/32 spacing scale; heading, content and action stay in one group.

The signature is a concrete, target-bound check entry: repository + selected
checkout + next check action. This is more useful than another aggregate score.

```text
Project / checkout                         Repository refresh
Next step: set up checks / run saved checks / inspect result
Current issues                             Latest check result
Advanced operations and configuration (secondary)
```

### Additive discovery contract

`POST /api/projects/discover-details` takes the same `{path}` as the legacy
discovery route, uses the same protected application service, and returns
`{repositories: [{name, path}], partial, warnings}` within the existing envelope.
The legacy route keeps its array response. Partial results are selectable, not
an implicit complete registration set. Registration without explicit selections
must fail rather than silently accept a truncated set. Cancellation is not
classified as invalid user input. Traversal remains read-only with finite depth
and entry limits; this does not claim interruptible OS calls or bounded directory
listing memory.

## Target-stack correction — 2026-09-10

Release authority and subsequent milestones are now defined in
[Project-oriented analysis](PROJECT_ANALYSIS_DESIGN_20260910.md); the original
no-release restriction at the end of this historical slice no longer governs
the later user-authorized work. Verification is still required before release.

The user clarified that their main company workload is Python/FastAPI and Vue.
The application's Go implementation language must not determine the target
project's quality-tool inventory. The current Go execution slice is a pilot,
not a complete first-use experience for that workload.

Next design priority: inspect project manifests and existing configurations,
identify backend/frontend roots and local environments, then offer applicable
checks. Prefer existing scripts and tool choices. Missing dependencies need a
project-specific setup preview (environment, exact commands, files changed),
not a bare missing-tool badge or global installation. Installation/configuration
changes require explicit approval; tests absent is distinct from tools absent
and from a passing result. Python/FastAPI and Vue runners are not implemented
or verified by this note. Keep all completed discovery, layout and safety fixes.

## Browser review findings during implementation

The first candidate was exercised in an isolated home on port 38481, with a
real one-statement Go fixture (not production measurement data). Registration
without a name worked. Go vet and coverage both ran successfully; the fixture's
100% coverage does not describe Dev Control Room's coverage. Seven routes had
no horizontal overflow at the browser's actual 485px viewport; console error
logs were empty for that session.

This review also found regressions to fix before acceptance: registration did
not expose a refreshed checkout, scan completion left stale UI state, the scan
button reverted to its old label, and the desktop code-check grid squeezed the
cards into its right column. Optional tool inventory also needed progressive
disclosure. These are iteration findings, not a final pass. See the separate
verification record for final build and test status.
